# 素材逐设计生成 v1.18.0 · 验证记录

日期：2026-10-25（Asia/Shanghai）。部署提交 `264b26f`，线上版本 `1.18.0`。
本记录只写实际跑过的调用与观察，不预先把并发、清晰度或“完整”说成保证。

## 一、并发上限实测（同一把火山方舟 Key）

对同一张拼图的不同设计同时发起整图清理请求，统计墙钟时间与失败：

| 并发 | 墙钟 | 单张耗时范围 | 成功 | 说明 |
|---|---|---|---|---|
| 4 | 20.7 s | 18.1–20.6 s | 4/4 | — |
| 8 | 23.0 s | 17.1–23.0 s | 8/8 | 与 1 张耗时基本相同 |
| 10 | 27.1 s | 18.6–27.1 s | 10/10 | 开始排队，吞吐未提升 |
| 12 | 28.7 s | 16.7–28.7 s | 12/12 | 排队更明显 |
| 16 | 34.3 s | 17.8–34.1 s | 15/16 | 1 张 `invalid_response` |

结论：**8 路**是性价比拐点；16 路出现“可能已计费但没拿到结果”的失败，不采用。因此
`DEFAULT_WORKERS = MAX_WORKERS = 8`。同账号多把 Key 共用额度，不用于绕开限流；
DeepSeek 池遇 429 全池冷却 60 秒的既有规则保持不变。

本地单张成本（不含 API，同一台服务器）：解码 + 转码 + 去白底 + 存盘约 1.75 s CPU，
8 张同时峰值内存 370 MB。

## 二、定位必须在整图清理之后

先尝试直接对带水印原图调用 DeepSeek 定位，两张测试图**都**返回：

```
定位范围不完整、重复或越界，请框选后重试。
```

因此保留一次整图清理，只为定位和构图服务；每个设计仍从**原图**的 12% 外扩小块生成，
不从清理图裁剪。

## 四、部署后端的端到端验收

用部署目录 `/opt/hsd-agent/current`（`264b26f`）里的 `MaterialManager` 直接接收一张
490×330 的拼图局部，走与员工网页相同的路径（接收 → 排队 → 执行 → 保存）：

- 状态 `ready`，源张 `done`，**75.2 s**，8 个设计全部 `needs_review`；
- 阶段顺序：`preparing → cleanup → locating → designs(0/8 → 1/8) → saving → done`；
- 进度文案由服务器拼装（`已完成 x / y 个素材。`），供应商原文不转发；
- 每项提示包含“模型重新绘制”“已去掉 N 处边缘杂块”等，触边项另有“可能被裁切”。

验收产生的 4 个临时任务目录已删除，未新增生产访问码，未改动口令、Key 或 Nginx。

## 六、已知限制

1. 模型会重画：文字、配色、细节可能和原图不同，全部结果仍需人工确认。
2. 部分设计保留原图的卡片底色（如米色、粉色底板），因为提示词要求保留内部底板；
   需要纯透明底时可对该项单独重做并写明要求。
3. 密集拼图会出现“与其他设计范围重叠”“设计范围不确定”的提示，个别设计可能带进
   相邻内容或被裁切，需逐张核对。
4. 每个设计单独计费；一张 40–55 个设计的拼图约 43–55 次生成。
5. 单批输出约 130–240 MB（42 张第一张实测 223 MB），数据卷剩余 4.6 GiB，三天保留
   期内约可容纳 20 批左右，需要留意余量。
6. 未做网页登录态上传验收（需要员工访问码）；改为同一后端路径的端到端调用，
   HTTP 层未改动。
