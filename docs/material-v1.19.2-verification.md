日期：2026-10-27。基线：`9c377ba`（v1.19.1）。本轮只改素材提取的自动识别环节与失败后的操作方式，图号助手的审核、编号与导出规则不变。

## 定位过程（只读核对线上真实任务）

读取线上最近的素材任务（不修改用户数据）：

- 失败任务 `e7a62e7f`：962 × 706 单张原图，`implementation` 为 v1.19.1，阶段历史为 `preparing → cleanup → locating → source_error`，
  失败记录只有一条 DeepSeek 定位尝试，code 为 `invalid_decision`，`settled` 为真（即服务端确认已返回、可以安全重试）。
- 对比此前成功任务：同一张 962 × 706 的图在 v1.19.0 下第一次定位也失败过，靠后续尝试才成功。
- 结论：定位环节把 DeepSeek 返回的**整个**候选列表当成一个整体校验——只要有一个框越界 1 像素、出现一个小数、或是重复/嵌套/落在灰色留边上，
  全部候选都被丢弃，整张图直接失败。员工因此只能手动框选。这是“老要框选”的根因，而不是图片本身有问题。

## 本次改动

1. 定位结果按“尽量保留”处理：越界坐标钳制到 0..1000、小数四舍五入；重复、嵌套、只覆盖灰色留边的候选只丢那一个并在批次说明里写明“有 N 个候选范围无法使用，已跳过”；
   只有**一个可用候选都没有**时才判定失败。这不会放宽安全边界——仍然不会凭空生成范围，只是不再让一个坏框毁掉整张图。
2. 定位失败自动重试一次：只针对“已确认返回、判定失败”的情况（`settled`），第二次请求换成只发原图、去掉坐标尺参考图，避免原样重发。
   计费状态未知（`settled=False`）时永不自动重发。
3. 贴边判定放宽：只有**又细又小**的贴边碎片才跳过（最短边 < 原图短边的 15%，或面积 < 原图 3%），贴边但完整的大图案照常生成；
   整张就是一张设计（占 85% 以上）仍然照常生成。
4. 失败原因更具体：全部候选都是贴边窄条时用独立错误码，页面文案说明是“贴着画面边缘且只剩很窄的一条”，不再与普通识别失败混在一起。
5. 失败的原图卡片多一个“自动重试”按钮：一键重跑这张图的清理、识别与生成，不需要拖框；只有在上一笔请求是否扣费尚未确定时隐藏该按钮（改用框选补提里的确认流程）。

## 审查记录

- 钳制只发生在坐标值本身，范围仍要求 `左 < 右`、`上 < 下`，坐标轴、留边移除、重叠提示逻辑保持不变。
- 丢弃候选时都会计数并写入批次说明，不会静默少图。
- 重试只在 `ArkProviderError.code == "invalid_decision"` 且 `settled` 为真时发生，最多一次；未知计费、鉴权、限流等错误立即上报，语义与既有“未确认不重发”一致。
- 失败卡片的“自动重试”调用既有的重做接口（只带 `source_id`，不带框），服务端对失败原图允许该路径；`submission_unknown` 时不显示该按钮。
- 未做任何程序化抠边、删白或裁切；未改动模型、并发上限、保留期规则。
